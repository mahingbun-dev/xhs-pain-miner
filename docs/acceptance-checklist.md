## M1② 人工盲评 20 张卡片 ⏳

**判定：≥ 12/20 张卡片的方向，你会真想去做。**

**前置**：一个可用的 LLM Key（`LLM_API_KEY` 等，见 `.env.example`）。可选：一件你
自己关心的品类关键词（比 fixture 的"防晒霜"更能反映真实判断）。

**步骤**

```bash
.venv/bin/xhs-pain-miner mine -k 防晒霜 -n 200 -o /tmp/盲评.html
```

打开 `/tmp/盲评.html`，取前 20 张卡片，**只看两件事**：卡片的方向、和它的证据摘要。
逐张回答一个问题：

> 「这个方向，我会不会真想去做？」

**判定规则**

- 记 20 个"是/否"，`是` 的条数 ≥ 12 即通过。
- **先别展开因子明细**。盲评评的是"这个方向值不值得做"，不是"分数算得对不对" ——
  后者会污染前者（看到 0.9 的提及量因子，很难不觉得它重要）。
- 每张卡片顺带记一句理由（"已有替代品"/"我不懂这个领域"/"确实想试"）。事后这句理由
  比"是/否"有用得多。

**产出物**：一张 20 行的表（卡片编号 / 方向 / 是或否 / 一句话理由）。

**要如实记录"否"** —— 有用率 55% 是个**有价值的结论**（说明选品环节需要改），
把它凑到 60% 才是真正的损失。

## M1③ 频次抽查误差 ⏳（机制下限已验证）

**判定：误差 < 15%。**

**前置**：装 `[analysis]` extra（`pip install -e ".[analysis]"`，会带来
sentence-transformers 与约 100MB 模型权重）。另外真实误差需要 LLM Key。

**两层含义要分开**

| | 怎么得到 | 现状 |
|---|---|---|
| **机制下限** | `.venv/bin/python tools/eval_clustering.py` 第四节。把 ground truth 当作"完美归纳出的清单"，因此只测分类机制本身 | ✅ 已自动验证 |
| **端到端误差** | 真实 Key 跑一次 `mine`，人工核对 3 个痛点的提及次数 | ⏳ 待做 |

端到端那一层**不能由脚本代劳**：脚本的 ground truth 是 fixture 里人工标好的
`truth_label`，而真实运行里"有哪些痛点"是 LLM 归纳出来的 —— 归纳漏掉一个痛点，
它的提及次数就直接归零，而这件事只有人工核对原文才看得出来。

**步骤（端到端那一层）**

1. 用真实 Key 跑一次 `mine`，拿到报告；
2. 随机抽 3 个痛点，按它的关键词在原文里**人工数一遍**真实提及数；
3. 与卡片上的「提及 N 次」比，算相对误差。

**产出物**：3 行（痛点 / 卡片上的次数 / 人工数出的次数 / 相对误差）。

## M1④ VLM 成本实测 ⏳

**判定：产出一份实测报告**（这一条要的是**数字**，不是达标线）。

**前置**：真实 **VLM** Key（图片分析用的模型，通常与文本 LLM 分开配置）。

**步骤**

```bash
.venv/bin/xhs-pain-miner mine -k 防晒霜 -n 200 --deep -o /tmp/deep.html
```

开跑前会打印成本预估并要求确认；`-y` 跳过确认。建议先用 `MAX_VLM_CALLS` 设一个
硬上限，避免第一次实测就烧掉远超预期的额度。

**要记录的数字**（都在 `MiningResult.cost` 里，终端摘要也会打印）

| 字段 | 含义 |
|---|---|
| `llm_calls` / `vlm_calls` | 实际调用次数 |
| `llm_input_tokens` / `llm_output_tokens` | token 量（算钱用） |
| `vlm_images` / `vlm_cache_hits` | 实际分析的图片数 / 命中缓存省下的次数 |
| `elapsed_seconds` | 总耗时 |

**金额**要按你所用模型的**当期价目**折算，并在报告里写明是按哪个模型、哪个价目算的
—— 架构文档 §4.3 里那句"¥15-100 视模型"至今是**预估**，这次实测的作用就是把它换成
真数字。

## M2 竞品调研人工抽检 ⏳

**判定：抽检的竞品里没有"把不相关的项目判为竞品"的情况。**

**前置**：能联网（脚本会真的去打 GitHub 与 iTunes 的接口；GitHub 匿名额度约
10 次/分钟，脚本自带节流）。

**步骤**

```bash
.venv/bin/python tools/eval_research.py --show-found
```

它会打印每条**召回的竞品**连同 URL 与平台描述。逐条点开核对该竞品的**定位**：

> 「这个东西，是在解决那个痛点吗？」

**判定规则**

- 脚本会同时输出自动指标（召回 / 误报 / 四值结论），但那只是**下界**：
  `expect_none` 只覆盖了"同名不同物"那一类能写成关键词的误报。
- 真正的准确率靠上面这一步的人工逐条核对。
- 三种典型误报形态，抽查时重点看：
  1. **同名不同物** —— 名字沾边、做的事情无关（实测样本：`防晒搓泥` 命中一个
     2.3 万星的**个人书籍收藏**仓库）；
  2. **平台侧不相关** —— `notes export` 命中的全是 Evernote / Notion 等**别家产品**
     的导出器；
  3. **相关性判定的漏网** —— 判定失败时候选会被**全量保留**（保守取舍），这时卡片上
     会标"未经相关性判定"，那批必须逐条看。

**产出物**：抽检清单 + 每条"相关 / 不相关"的判断，以及不相关的那几条的具体理由。

## M3① 真实后端跑通一个品类 ⏳

**判定：用真实采集后端完整跑通一次 `mine`，产出的报告里证据链能点回真实笔记。**

**前置**

1. 本机装有 [xhs-collector](../../xhs-collector)（自研采集器，**ego-lite 浏览器基座**，
   `uv pip install -e` 进主项目 venv），且 **ego lite 里已登录小红书**（未登录时
   采集器会自动弹码引导扫码）；
2. 一个 LLM Key（跑 `mine` 需要）；
3. 一件你关心的品类关键词 —— 别用 fixture 的"防晒霜"，用真东西才看得出问题。

**步骤**

```bash
export COLLECTOR_BACKEND=plugin
export XHS_COLLECTOR_PLUGIN=xhs_collector.backend
.venv/bin/xhs-pain-miner collect -k <你的品类> --backend plugin   # 先单独验证采集层
.venv/bin/xhs-pain-miner mine   -k <你的品类> --backend plugin -o /tmp/real.html
```

**判定规则**

- `collect` 与 `mine` 都正常结束，报告里的**证据链「查看原文」链接能点开**回到
  真实笔记 —— 这是"证据链"这个卖点的最低验证（PR #14 补上的能力）；
- 核对运行提示里那条"本次只取到 N 篇笔记"的警告是否符合事实。

**⚠️ 预期与现实要对上**：一次搜索只返回**一页**（约 20-40 张卡），`-n 200` 达不到。
这是上游页面形状（搜索页不滚动、无翻页参数），**别把它当成 bug 去修，也别把它当成
"跑通了 200 篇"**。小语料的聚类也会偏粗（8 篇曾挤成 1 个大簇），M1③ 的人工核对
建议用 `-n 20` 左右的语料。

**产出物**：一次真实运行的报告 + 3 条点开核对过的证据链。

**2026-09-19 实测记录**：「防晒霜」关键词，`-n 8` 与 `-n 20` 两轮全部正常结束，
真实评论（安耐晒/兰蔻/补涂/防晒指数……）进入语料；`-n 8` 轮的报告已确认渲染出
含 `xsec_token` 的「查看原文」链接。剩人工点开 3 条核对。

## M3② 代码审计（仓库不含受限代码）✅

**已通过（2026-09-19 签署）。** 复跑方式与历史记录见 [code-audit.md](code-audit.md)。

**为什么它是验收门而不是"顺手做一下"**：本项目是 Open Core（开源引流 + 云端订阅），
一旦仓库里混进 MediaCrawler 那类"非商业学习许可"的代码，**你后续的商业化与融资都会
带着这个权属瑕疵**。这件事的成本随时间是复利增长的。

**步骤**

下面六条都跑一遍，**逐条对照"期望结果"**。命令刻意写得窄：一条会喷几十行误报的审计
命令，跑一次就不想跑第二次（初版就是那样 —— `sign` 会命中 `design`，`chrome` 会命中
竞品调研的渠道名）。

```bash
# ① 签名逆向 / 加密相关 —— 期望：无任何命中
grep -rnE "\ba1\b|web_id|webId|xsec_sign|encrypt" src/ --include="*.py"

# ② 浏览器自动化 —— 期望：无任何命中（不要用 "chrome" 做模式，它是竞品调研的渠道名）
grep -rnE "playwright|selenium|pyppeteer|puppeteer|\brod\b|\bcdp\b" src/ --include="*.py"

# ③ 第三方采集器特征串 —— 期望：只命中"解释许可证边界"的注释，没有代码
grep -rniE "mediacrawler|spider_xhs|xhs-downloader" src/ tests/ tools/
grep -rniE "mediacrawler|spider_xhs|xhs-downloader" docs/     # 文档里提到是允许的

# ④ 采集层里的网络调用 —— 期望：只有 mcp.py 一处，且打向本机服务
grep -rnE "httpx\.|requests\.|urlopen|socket\." src/xhs_pain_miner/collectors/
grep -rnoE "https?://[a-zA-Z0-9.-]+" src/xhs_pain_miner/collectors/*.py | sort -u

# ⑤ 核心依赖 —— 期望：只有 CLI / 配置 / LLM 适配所需的包
sed -n '/^dependencies = \[/,/^\]/p' pyproject.toml

# ⑥ 采集层的文件清单 —— 期望：只有 7 个文件，没有采集实现
git ls-files src/xhs_pain_miner/collectors/
```

**判定规则**

| 命令 | 期望结果 | 为什么 |
|---|---|---|
| ① | 无命中 | 签名逆向是《反不正当竞争法》2025 修订第 13 条第 3 款的构成要件，也是蝉小红案 490 万的直接依据 |
| ② | 无命中 | 仓库不该依赖任何浏览器驱动；采集发生在**用户本机运行的那个服务里**，不在本仓库 |
| ③ | 只命中注释 | 提到 MediaCrawler 是为了解释**为什么它不能进仓库**；判据是"有没有它的代码"，不是"有没有它的名字" |
| ④ | 只命中 `mcp.py`，且**只有一行是真正的调用** | `collectors/` 里唯一会发请求的是 `httpx.Client(...)`（`mcp.py:418`），打向用户本机的 `XHS_MCP_URL`（默认 `127.0.0.1:18060`）；同一文件里其余命中是类型标注与异常处理。`xiaohongshu.com` 只出现在拼**证据链链接**的字符串里，不发请求 |
| ⑤ | 无采集库 | `mcp` 后端**不引入任何新依赖**（复用已有的 `httpx`）—— 这一点本身就是可审计的证据 |
| ⑥ | 7 个文件 | 协议 / 样例 / 插件加载器 / 工厂 / 模板 / MCP 适配器 / `__init__`。没有任何平台采集实现 |

> **`src/xhs_pain_miner.egg-info/` 是本地构建产物**，不在版本库里（`.gitignore` 里有
> `*.egg-info/`）。它里面的 `PKG-INFO` 是某次 `pip install -e` 时的 README 快照，
