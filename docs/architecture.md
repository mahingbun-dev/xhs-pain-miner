## 二、数据流

```
关键词
  │
  ▼
[1] 采集      CollectorBackend.collect()  →  RawCorpus
  │            （RawNote + RawComment，个人信息已哈希）
  ▼
[2] 清洗      去重 / 过滤广告与水印 / 归一化  →  list[TextUnit]
  │
  ▼
[3] 向量化    embedding（默认本地 bge-small-zh）  →  ndarray
  │
  ▼
[4] 痛点归集  LLM 归纳痛点清单 + embedding 分类  →  痛点簇
  │            （size 即「提及次数」= 分类到该痛点的条数）
  │            ★ 不逐条调 LLM —— 见 4.1
  │            ★ 痛点名**不再直接当检索词**：它描述"问题"，竞品是"解法" —— 见 4.5
  ▼
[5] 属性标注  每个痛点调一次 LLM  →  情感 / 趋势 / 实现难度
  │
[6] 竞品调研  每个痛点：LLM 翻成「解法检索词」（按渠道分语言）
  │            → 逐条分发到已接入的渠道（GitHub / App Store）
  │            → LLM 判定相关性（一次调用判定全部候选）
  │            → ResearchOutcome（结论 + 检索轨迹 + 竞品列表）
  │            ★ 「查证过确实没有」与「这次没查成」必须分开 —— 见 4.5
  ▼
[7] 评分      多因子加权  →  OpportunityCard(score, score_breakdown, research_status)
  │
  ▼
[8] 渲染      单文件 HTML / Markdown / 终端表格（四种调研结论说四句不同的话）
```

## 四、关键设计决策

### 4.1 为什么是「LLM 归纳 + 分类」而不是聚类

`PainCluster.size`（提及次数）是整个产品最核心的指标，用户会拿它做判断。
它必须是**算出来的、可复现、可核对**的 —— 这一点没有妥协。

M1 最初用 HDBSCAN 聚类来实现它，端到端跑真实本地模型后发现**这条路走不通**：

| 方案 | purity（没乱聚） | coverage（没切碎） |
|---|---|---|
| HDBSCAN mcs=3 | 0.996 | **0.095** |
| KMeans k=10 | 0.532 | 0.537 |
| 两阶段（HDBSCAN + 质心合并） | 0.339 | 0.766* |

> ``coverage`` 的口径是**噪声不算一个簇**（见 `cluster_quality`）。早期记录里
> HDBSCAN 那一行是 0.107 —— 那是把噪声当成一个正常簇算出来的虚高值。修正后
> 结论只会更强：真实痛点被切得比原先记录的更碎。带 `*` 的「两阶段」一行是
> 早期一次性探索结果，当前脚本无法复现。

1142 条文本聚出 171 个簇，而语料里只有 10 个真实痛点 —— HDBSCAN 把「搓泥」
这个 130 条的真实痛点切成了 16 片，每片 `size` 只有 8。用户一核对就会发现对不上。

根因是**中文短文本的语义区分度不够**：同主题相似度 0.62 对跨主题 0.56，
信噪比只有 0.06（手写对照语料的数字；内置 fixture 合成语料是 0.087，同样很低）。
四条独立证据（换模型、调参、簇合并、手写自然语料对照）都指向
同一结论，详见 [`pipeline/taxonomy.py`](../src/xhs_pain_miner/pipeline/taxonomy.py)
的模块文档。复现：`.venv/bin/python tools/eval_clustering.py`。

**替代方案：把「无监督聚类」换成「LLM 归纳清单 + embedding 分类」。**
「给定一组已知的痛点标签，判断这条文本讲的是哪个」比「从零发现有哪些痛点」
容易得多 —— 前者只需要相对比较，后者需要发现结构。实测分类准确率：

| LLM 只标注 | 分类准确率 |
|---|---|
| 5% 样本 | 0.747 |
| 10% 样本 | 0.803 |
| 20% 样本 | 0.870 |

成本上：聚类方案是**每个簇一次**（实测 171 次 —— 正因为它把一个痛点切成了十几片），
分类方案是 1 次归纳 + 每个痛点 1 次标注（10 个痛点 = 11 次）。省下来的不是"分类比
命名便宜"（同样 10 个痛点的话是 10 vs 11），而是**不必为上百个碎片各命名一次**。
`size` 在新方案下
是**分类到该痛点的文本条数**，同样可复现、可核对，但不再有切碎的问题。

`cluster.py` 的 HDBSCAN 路径保留为备选（`PAIN_DISCOVERY=cluster`），用于在有
真实语料时对比；LLM 完全不可用时也会自动降级到它，并在报告里如实说明
「提及次数偏小，请以证据链为准」。

### 4.2 为什么采集层要插件化

第三方采集器的许可证往往不允许商业使用或再分发（MediaCrawler 的 "非商业学习许可 1.1" 即是）。
把它们放进仓库会让项目从内部违反上游许可，并污染所有下游使用者的权属。

因此本仓库采取与 Playwright 相同的策略：**只定义协议，不携带实现**。

```
你的仓库（AGPL-3.0）
  └─ collectors/          只有协议 + 适配器 + 样例数据
                            ✗ 没有任何真实的平台采集代码

用户本机
  └─ 用户自己合法持有的采集器
       └─ 用户按协议写的薄适配器
            └─ XHS_COLLECTOR_PLUGIN 指向它
```

详见 [collector-plugin.md](collector-plugin.md)。

### 4.3 成本模型与 VLM 控制

以「200 篇笔记 + 2,400 条评论 + 1,000 张图」为基准（**按默认路径 = LLM 归纳 + 分类**计）：

| 阶段 | 方案 | 预估成本 | 预估耗时 |
|---|---|---|---|
| embedding | 本地 `bge-small-zh`（CPU） | ¥0 | 10-20s |
| 痛点归集 | LLM ×1（归纳清单）+ ×N（每个痛点一次属性标注）→ 10 个痛点 = 11 次调用 | ¥0.2-0.5（DeepSeek） | 1-2min |
| ↳ 分类 | embedding 余弦比对，**不产生额外 LLM 调用** | ¥0 | <1s |
| 竞品调研 | GitHub API 免费额度 | ¥0 | 10-30s |
| **VLM 图片** | 1,000 次调用 | **¥15-100（视模型）** | **10-30min** |

> 上表不含备选路径 `PAIN_DISCOVERY=cluster`（HDBSCAN，¥0、<5s）：它把一个真实痛点
> 切成十几片，标注调用数会按**簇数**增长（实测 171 个簇 → 171 次调用），量级与
> 默认路径完全不同。见 4.1。


**VLM 是最大成本与耗时项，用户自带 Key 时对成本极度敏感。控制策略（M1 必须全部落地）：**

1. 图片 URL 哈希去重（同款商品图跨笔记大量重复）
2. 长边压缩至 512px 后再上传（`VLM_IMAGE_MAX_EDGE`）
3. 单篇最多取前 3 张图（`VLM_MAX_IMAGES_PER_NOTE`）
4. 按图片 hash 缓存 VLM 结果到 SQLite
5. 并发 + 限流 + 指数退避
6. **失败降级**：VLM 调用失败不阻塞主流程，卡片标注"图片分析缺失"
7. **开跑前打印成本预估**，`MAX_VLM_CALLS` 可设硬上限

### 4.4 机会分公式

```python
机会分 = 100 × (
    0.25 × 痛点强度     # 情感极性 × 强度
  + 0.20 × 提及量       # log 归一 × 绝对置信度（50 次提及饱和）
  + 0.20 × 增长趋势     # 时间序列
  + 0.25 × 竞品空白度   # 竞品调研结论（GitHub / App Store；没查成 → 中性 0.5）
  + 0.10 × 实现难度⁻¹   # LLM 评估
)
```

每个因子都写入 `OpportunityCard.score_breakdown`，可逐项展开溯源，**权重可调**。
这是与黑箱评分产品的核心差异点。

**「提及量」为什么是两项相乘** —— 它同时回答两个不同的问题：

| | 项 | 回答的问题 |
|---|---|---|
| 相对项 | `log1p(size) / log1p(max_size)` | 在这份语料里排第几 |
| 绝对项 | `min(1, log1p(size) / log1p(50))` | 证据够不够硬（置信度） |

只有相对项时，任何语料里最大的那个痛点恒等于 1.0（`log1p(max)/log1p(max) ≡ 1`）——
一个只被 12 次提及的痛点在薄语料里会和 543 次提及的痛点同分。绝对项补上这个锚点，
于是因子取到 1.0 的含义从「只要最多」变成「最多**且**证据充分」。

两项相乘而非取 `min`：`min` 在 `max_size` 已达 50 时恒等于相对项，绝对项就只在薄
语料里生效了，健康语料里同样证据不足的尾部簇拿不到任何折扣。

语料规模偏小（最大痛点不足 50 次提及）时，报告会在「运行提示」里显式说明 ——
否则用户看到头名的「提及量 0.65」会以为算错了。

`competitor_gap` 的取值与调研结论一一对应：

| `research_status` | 含义 | 空白度 |
|---|---|---|
| `ok` | 查到竞品 | 有活跃竞品 → 按数量与热度下调（≤ 0.60）；**全部停更 → 0.75** |
| `no_competitor` | 查证过，平台搜得到但没有相关的实现 | **1.0**（最强的正面信号） |
| `unsearchable` | 检索不到 / 没有可用的检索词，无法判断 | 中性 0.5 |
| `failed` | 这次没查成（限流 / 网络 / 接口变更 / 响应格式异常） | 中性 0.5 |

后两行**必须**取中性值：0 命中不是"没有竞品"。M1 曾把 0 命中读成"查证过确实没有"，
每张卡片因此虚高 12.5 分，报告上还会印"✅ 未发现竞品"—— 用户于是去做一个实际
已经很拥挤的方向（见 4.5）。

### 4.5 竞品调研：从「痛点名搜索」到「解法词搜索」+ 结论契约

M2 修的是一个**方向性**缺陷。M1 拿痛点名当检索词去搜竞品：

| 查询词 | 类型 | 召回 |
|---|---|---|
| `防晒搓泥` | 痛点名（问题） | **0**（App Store）／**1 条无关**（GitHub：一个 2.3 万星的书籍收藏仓库） |
| `美妆 成分查询` | 解法词（方案） | 美丽修行(10913 评分)、你今天真好看(36491 评分) |
| `小红书 收藏 备份` | 解法词（方案） | 蛋啵(39718 评分)、百度网盘(927283 评分) |

> 数字取自 2026-09 的真实请求。**论证不依赖任何单个数字** —— 依赖的是"痛点名与
> 解法词没有交集"这件事，而 `tools/eval_research.py` 可以随时复跑三组对照验证它。
> 上表那 1 条无关命中同样是 M1 的失败形态之一：它会被算成"活跃热门竞品"，
> 反过来**压低**空白度（与"0 条 → 空白度 1.0"是同一个方向性缺陷的两面）。

痛点名描述**问题**，竞品是**解法**，两者词汇没有交集 —— 0 命中是必然的。
而 M1 又把 0 命中解读成"查证过确实没有竞品"（空白度 1.0，机会分里最强的正面
信号）。两个错误叠加的结果是：报告把一个已经拥挤的方向说成空白。

所以 M2 的竞品调研由四步组成，每一步各自可验证：

1. **翻译**（`research/query.py`）：LLM 把痛点翻成"用户真的会敲进搜索框"的词，
   并标注该词适合发往哪个渠道（实测 App Store 认中文、GitHub 认英文）。
   **失败时绝不退回用痛点名兜底** —— 那等于把 M1 的错误重演一遍。
2. **路由**（`pain_miner._research_clusters`）：只把检索词发往**已接入**的渠道
   （GitHub / App Store）。未接入渠道（chrome / xhs）的词直接跳过 —— 为它们伪造
   一条"这次没查成"的轨迹，会让 `merged` 的保守规则把每个簇的 `no_competitor`
   压成 `unsearchable`，把 M2 唯一的正面信号系统性丢掉。
3. **判定**（`research/relevance.py`）：LLM 一次判定该簇全部候选（一次调用，
   成本不随候选数线性增长）。失败时**全部候选留在竞品列表里**（保守取舍，
   宁可多给几个链接，也不断言"没有竞品"），并带着"未经判定"的警告一起交付。
4. **出结论**（`research/outcome.py`）：`classify_status` 依据**平台有没有对这个
   查询返回过东西**判出四种状态之一，连同检索轨迹（搜了什么词、平台回了多少条、
   留下几条、哪次失败）一起写进 `ResearchOutcome`。

结论一路上行到卡片（`OpportunityCard.research_status`），渲染层据此说四句话 ——
**"检索不到"与"查证过确实没有"在报告里长得不一样**，用户能看懂下一步该做什么。

#### 一条贯穿全程的规则：主张只能由知道答案的那一层发出

上面四步各自会产生**给人看的文案**，而它们对同一件事的"知情程度"差别很大：

| 层 | 它知道什么 | 它**不知道**什么 |
|---|---|---|
| 渠道层（`github` / `appstore` 的 `RuntimeError`） | 这一次请求成功还是失败 | 同渠道别的检索词结果、其它渠道结果、最终结论 |
| 轨迹层（`QueryTrace.error`） | 这一次查询发生了什么 | 同上（它是**给人复核用的**，不是给评分用的） |
| 渠道结论层（`warning_for`） | 该渠道全部检索结果 | **合并之后**是什么结论 |
| 结论层（`_unresolved_warning`、渲染层的卡片结论） | 合并后的卡片，即最终结论 | —— |

「知道答案的那一层」**不止一个**：`_unresolved_warning` 与渲染层读的都是合并后的
卡片，还有 `pain_miner` 里几条"压根没查"的分支（调研关闭 / 超出
`RESEARCH_MAX_CLUSTERS`）—— 它们本来就知道结果是中性，同样在说、且说对了。
规则是**渠道层与轨迹层不许说**，不是"只有某一个函数能说"；把它写成绝对句，
本身就是一种契约外的主张。

M2 自审里改掉的三处失实文案，是**同一条规则**的三个违约点：渠道警告里写"其「竞品
空白度」按中性值计"（合并后可能不是中性）、轨迹里写"必须按中性值处理"（在"已查到
竞品 + 另一条检索词被限流"这条可达路径上是假话）、`appstore.py` 的 `Raises:` 契约
同样这么写。三处都改成了只陈述自己这一层确实知道的事。

**新增文案前先问两句**：
1. 这句话在我的位置上**一定**为真吗？
2. 我是不是把它写成了**绝对的**（"只有……"、"唯一……"）？绝对句里只要有一个反例，
   它就变成了一条新的失实文案 —— 本轮与上一轮的两次返工都出在这上面。

被拼进上层的每一句话，都会在合并、过滤、降级之后被重新审视一遍。

### 4.6 隐私与合规设计

`OpportunityCard.to_public_dict()` 是**唯一**允许离开本机的序列化路径：

- 白名单字段：`score` / `score_breakdown` / `feasibility` / `research_status` /
  痛点的簇级统计 / 竞品公开信息（含平台上的公开 `description`）
- **原文（`Evidence.text`）与所有 `*_hash` 字段在结构上不进入载荷**
- 运行提示（`MiningResult.notes`，含降级说明与 LLM 回复预览）**不进入载荷**
- 个人信息一律哈希（`hash_id`），且哈希前可加本地盐值（`HASH_SALT`）
- `SHARE_RESULTS` 默认 `false`，必须由用户显式开启

**两道防线，不要混淆它们的强度：**

| | 防线 | 强度 |
|---|---|---|
| 1 | 结构剔除 —— `Evidence.text` 不进入 `to_public_dict()` 的载荷 | **强**，有守卫测试（`test_public_dict_never_leaks_raw_text`） |
| 2 | 回抄检测 —— 对 LLM 生成的自由文本做原文比对 | **必须**，但尚未接入（M4 实现上传时才需要） |

第 2 道防线存在的原因：`title` / `pain.label` / `pain.summary` / `gap_notes` 是 **LLM 生成的
自由文本**，而"摘要时引用原话"是模型的常规行为，结构性剔除拦不住它。
`models.find_verbatim_overlap()` 提供了这个检测（n-gram 滑窗，默认 15 字阈值），
M4 的众包上传路径**必须**在出网前调用它。

**任何新增字段都必须先通过守卫测试**，并明确它属于哪一类 —— 结构性安全，还是需要回抄检测。
