# MCP 采集后端（对接 xiaohongshu-mcp）

采集层有三个后端，分工见 [collector-plugin.md](collector-plugin.md)：

| 后端 | 实现位置 | 什么时候用 |
|---|---|---|
| `fixture` | 本仓库（脱敏样例） | CI / Demo / 离线体验完整流程 |
| `plugin` | **你本机自备** | 你有自己的采集器（含 MediaCrawler 这类许可受限的） |
| `mcp` | 本仓库的**适配器** + 你本机运行的 [xiaohongshu-mcp](https://github.com/xpzouying/xiaohongshu-mcp) | 想真采一个品类，又不想自己写采集器 |

这一页讲第三个。

---

## 为什么它可以在仓库里，而 MediaCrawler 的适配不行

规则没变：**本仓库不携带任何第三方采集实现**。`mcp` 后端是这条规则的一个**有边界的例外**，边界就是许可证：

| 上游 | 许可证 | 能否随本仓库分发 |
|---|---|---|
| `xiaohongshu-mcp` | **Apache-2.0** | ✅ 可商用、可再分发、无附加限制 |
| MediaCrawler 一类 | 「非商业学习许可」 | ❌ 只能由你自备（`plugin` 后端） |

即便如此，`src/xhs_pain_miner/collectors/mcp.py` 里也**没有一行采集代码** —— 采集由你本机运行的 `xiaohongshu-mcp` 完成，本仓库只调用它的 HTTP 接口并做字段映射。

> **走的是哪套接口**：`xiaohongshu-mcp` 同时提供 REST（`/api/v1/*`）与 MCP 协议（`/mcp`）两套接口，同一个进程、同一个端口、同一份数据。本适配器走 **REST**，理由写在 `mcp.py` 的模块文档里。后端名仍叫 `mcp`，因为它对接的是 **xiaohongshu-mcp 这个服务**，不是"某种传输协议"。

## 一、先装并登录 xiaohongshu-mcp

这一步在**它自己的仓库**里完成，本仓库不参与。

```bash
# 1. 从 Releases 下载对应平台的二进制（macOS ARM / Windows x64 / Linux x64）
#    https://github.com/xpzouying/xiaohongshu-mcp/releases

# 2. 先运行登录工具，扫码登录（登录态由它自己保存在本机）
./xiaohongshu-login-darwin-arm64

# 3. 再启动服务（默认监听 127.0.0.1:18060）
./xiaohongshu-mcp-darwin-arm64
```

也可以用 Docker（它暴露 18060 端口）。

**服务起来之后，先确认它自己认得出来：**

```bash
curl -s http://127.0.0.1:18060/health
```

> ⚠️ **同一个小红书账号不能在多处网页端登录。** 登录了 xiaohongshu-mcp 之后，不要再在浏览器的网页端登录同一个账号 —— 会把它踢下线（反过来也一样）。
>
> ⚠️ **服务只监听本机。** 不要把 `XHS_MCP_URL` 指向公网地址：那等于把登录态交给远端服务，既超出本工具的定位，也让"数据不离开本机"这条设计失效。Docker 部署时用 `http://host.docker.internal:18060`。

## 二、配置本仓库

```bash
export COLLECTOR_BACKEND=mcp
xhs-pain-miner doctor            # 先确认后端被识别、服务可达、账号已登录
xhs-pain-miner collect -k 防晒霜 --backend mcp
xhs-pain-miner mine -k 防晒霜 -n 200 --backend mcp -o /tmp/report.html
```

| 环境变量 | 默认值 | 说明 |
|---|---|---|
| `COLLECTOR_BACKEND` | `fixture` | 设为 `mcp` |
| `XHS_MCP_URL` | `http://127.0.0.1:18060` | 服务地址 |
| `XHS_MCP_TOKEN` | 空 | 服务端启用了鉴权（它自己的 `AUTH_TOKEN`）时才需要 |
| `XHS_MCP_TIMEOUT` | `120` | 单次请求超时（秒），见下文"耗时" |

> **本后端没有 cookie 配置项。** 登录态由 `xiaohongshu-mcp` 自己保管，本程序不接触、也不需要你的 cookie。

## 三、三个硬约束（用之前请先读）

### 1. 一次搜索只有一页 —— `-n 200` 拿不到 200 篇

`xiaohongshu-mcp` 的搜索接口是"导航到搜索页 → 读页面初始状态 → 返回"，**不滚动、没有 cursor**。所以 `-n` 只能**截断**，不能**扩张**：一次搜索拿到的就是搜索结果首页那批。

`collect` 会在这种情况下把它写进运行提示，不会假装采全了：

```
⚠️  本次只取到 20 篇笔记，少于要求的 200 篇：xiaohongshu-mcp 的搜索接口一次
    只返回一页（搜索词「防晒霜」），上游不滚动、也没有翻页参数，所以重试不会
    变多。需要更大的语料请换关键词分多次采集。
```

**要更大的语料，就换关键词分多次采集。** 这是你主动的选择，不该由适配器偷偷放大请求量 —— 请求量直接等于风控风险。

### 2. 每篇笔记要再单独请求一次

搜索结果的卡片里**只有标题与封面，没有正文**，而正文是文本分析的主要对象。所以 N 篇笔记 ≈ N+1 次请求，而服务端每次请求都开一个浏览器页面。

| | 单次 `collect -k 防晒霜` |
|---|---|
| 请求数 | 1 次搜索 + 约 20 次详情 |
| 耗时 | 通常几分钟（详情走慢路径时更久） |

### 3. 评论：按需走快路径或慢路径

| `--comments` | 发给服务的参数 | 代价 |
|---|---|---|
| ≤ 10 | `load_all_comments: false` | 快，不滚动 —— **但拿到的可能是页面首屏那几条，少于你要的**（见下） |
| > 10（**默认 20**） | `load_all_comments: true` + `max_comment_items: N` | 慢，滚动加载，风控暴露更大 |

只展开**一级评论**，不点开二级回复的"更多"按钮：那点长尾回复的收益远小于"每篇多一次点击 + 等待"的代价。

> **快路径可能拿得比你要的少，而且是静默的。** 上游 README 说 `load_all_comments=false`
> 会给"前 10 条一级评论"，但这个 10 在上游源码里**找不到对应实现** —— 快路径既不滚动
> 也不截断，返回的就是页面初始状态里恰好有的那批，首屏只有 3 条就是 3 条。所以
> `--comments` 调到 10 以内换来的是"快、但可能少"。要确保拿满就把 `--comments` 调到
> 10 以上（**默认值 20 已经在慢路径上**，这也是它默认取 20 而不是 10 的原因）。

## 四、耗时与风控

**平台侧有风控。** 本项目自己的实测记录是：持续批量请求后，已登录账号会被踢下线（约 108 条后触发，见 [collector-plugin.md](collector-plugin.md) 的合规红线一节）。这不是本工具的 bug，也无法由本工具绕过 —— 本工具**不做**签名逆向、不换 IP、不换账号，那既违反上游许可，也正是《反不正当竞争法》2025 修订第 13 条第 3 款的构成要件（详见 [competitive-analysis.md](competitive-analysis.md)）。

实际建议：

- 一次跑一个品类，别连着跑十几个；
- 别为了凑语料把 `--comments` 调得很大；
- 出现"被踢下线"的迹象（大量请求失败）时**停下来**，重新扫码登录后再跑 —— 适配器会在失败率过半时主动中止整次采集，而不是交出一份缩水的语料。

**超时**：`XHS_MCP_TIMEOUT` 默认 120 秒。它比其它渠道（15 秒）大一个量级，因为服务端要开浏览器。但它**比上游给自己留的余地小**（上游详情接口的超时是 10 分钟，导航与点击前后还各带拟人延时）。也就是说默认值是"宁可失败也不无限等"的取舍：网络慢或评论特别多时，一次合法但很慢的请求会被掐断，表现为"这篇取详情失败"并计入运行提示。确实要等就调大它。

## 五、故障排查

`xhs-pain-miner doctor` 会先查服务的 `/health`（服务在不在），再查 `/api/v1/login/status`（账号登没登）。**这两件事会分开报**，因为它们需要完全不同的处理。

| 现象 | 原因 | 怎么办 |
|---|---|---|
| `无法连接 …` | 服务没起 / 地址不对 | 启动 `xiaohongshu-mcp`；确认 `XHS_MCP_URL` |
| `HTTP 401` | 服务端开了鉴权，token 不对 | 把服务端 `AUTH_TOKEN` 的值写进 `XHS_MCP_TOKEN` |
| `HTTP 500` + "账号未登录" | **登录态失效**（上游没有登录前置检查，未登录表现为 500 而不是 401） | 重新扫码登录 |
| `HTTP 500` + "账号仍处于登录状态" | 页面加载失败或被平台风控 | 稍后重试；持续出现看服务端日志 |
| `响应结构与预期不符：… 里缺少 ['desc']` | 上游或小红书页面结构变了 | **不要重试**，是适配器需要更新 —— 请提 issue |
| `返回的不是合法 JSON` | 地址指到了别的服务上 | 确认端口没被别的东西占用 |
| 大量"取详情失败" | 风控 / 超时太短 | 停一会儿；或调大 `XHS_MCP_TIMEOUT` |

> **"本次的提及次数可能因此偏小"** —— 只要出现"有 N 篇取详情失败、未计入语料"，卡片上的「提及 N 次」就**可能**低于真实值。说"可能"而不是"一定"，是因为那几篇本来也可能进不了语料（命中广告话术被整条丢弃、或与已有文本逐字相同被去重合并）。无论如何它**不等于**"这个品类没人提"。适配器把这句话写进运行提示，就是为了不让这两种情况长得一样。

## 六、合规红线（不可绕过）

采集能力由 `xiaohongshu-mcp` 提供，但**使用者仍然是你**。以下几条对本项目、对你都成立：

1. **不要绕过技术保护措施** —— 不要做签名逆向，不要用 IP 池 / 账号池规避风控。这是判例的直接依据（蝉小红案 490 万，见 [competitive-analysis.md](competitive-analysis.md)）。
2. **个人信息最小化** —— 本适配器只取 `userId` 并**立即哈希**，昵称、头像、IP 属地一律不取、不存。上游响应里这些字段都有，是被适配器丢掉的。
3. **不要对外提供数据** —— 本工具是**本地分析**工具。采集结果不要上传、不要转售、不要做成公开数据服务。判例打击的是"提供数据"，不是你本地算出了什么结论。
4. **只在你合法有权访问的范围内使用** —— 遵守小红书的服务条款与 `robots.txt`。

## 常见问题

**Q：为什么不直接用 `/mcp` 那个 MCP 协议端点？**
数据一模一样（`routes.go` 把两者挂在同一个 `AppServer` 上），但 MCP 那条路把 JSON 塞进 `content[].text` 字符串里，调用方还要再解一次；而官方 MCP SDK 是 async 优先，本仓库全程同步。理由的第一步列了三条，见 `src/xhs_pain_miner/collectors/mcp.py` 的模块文档。

**Q：为什么 `-n 200` 没采到 200 篇？**
见第三节第 1 条 —— 上游搜索只有一页。

**Q：采集会不会把我的账号搞封？**
本工具不做任何规避风控的事，但**批量请求本身**就有风险。建议一次跑一个品类、不要把 `--comments` 调太大、出现异常就停下来重新登录。

**Q：适配器会更新吗？**
上游的响应是小红书页面内部状态的透传，不是设计过的 API，随时可能变。适配器会**明确
报错并指出缺失的字段路径**，而不是静默产出空数据 —— 但它拦的是**有限的一批**。
下面把它拦什么、不拦什么分开写清楚。

**一、键存在性校验**（该字段在上游 Go 结构体里的 json tag 没有 `omitempty`，所以键恒存在，"键不见了"只可能是结构变更；值可以是 `null`）

| 路径 | 不校验时的**实际**后果 |
|---|---|
| `data.feeds` | 空语料，且被误报成"关键词不好，换个词" |
| `note.desc` | 正文变空串 |
| `note.title` | **静默退回搜索结果里的截断标题**（不是空 —— 看起来只是短了点） |
| `note.interactInfo` | **静默退回搜索卡片上的计数**（不是空 —— 看起来只是小了点） |
| `note.imageList` | 图片归零，`--deep` 什么都不做却看起来一切正常 |
| `comments.list` | 评论归零，像"这篇笔记没有评论" |
| 评论 `content` | **整批评论静默消失**（正文全变空串 → 全部被丢） |
| 评论 `subComments` | 二级评论静默消失 |

**二、形状 / 类型校验**（同样会立刻报错，但不属于"字段改名"这一类）

信封或结构体本身不是对象、数组字段不是数组、响应不是合法 JSON、HTTP 非 200、
200 但响应体不是这个服务的格式。

**另有一类是"每篇级"的，表现不同**：搜索卡片缺 `xsecToken` 时那一篇会被跳过并计入运行
提示，**失败率过半才会中止整次采集**（与上面两类"立刻报错"不一样）。实测：3 篇里缺 1 篇
只是多一条提示，2 篇都缺才抛错。

**三、仍然静默的**（改错了不会报错，只会安静地少一点东西）

- `note.time` 缺失 → 那些笔记的证据失去时间戳，「增长趋势」因子会变
  （实测 0.1667 → 0.2000；丢得足够多时会**直接退回中性 0.5**）；
- 评论 `likeCount` / `createTime` 缺失 → 走保守取值 `0` / `None`，同样**会改分数**
  （`likeCount` 缺失可让「痛点强度」减半；`createTime` 缺失实测让「增长趋势」
  从 0.1667 退回中性 0.5）；
- 评论 `id` 缺失 → 合成一个稳定的 id（这是设计好的兜底，不是问题）；
- 数组里的条目不是对象 → 静默跳过那一条。

> 所以看到任何"数量明显不对"或"分数说不通"的结果，都值得怀疑一次结构变更，
> 而不只是怀疑关键词或采集量。

看到第一类或第二类报错请提 issue。
